# OpenRouter: инструкция для ответственного за сервер Funban

## Статус перед передачей

Адаптер реализован, но реальный запрос с выбранной моделью ещё не проверен. Эта инструкция не является разрешением на слияние в main или деплой. Перед выпуском нужен успешный CI на итоговом коммите PR и отдельное решение о развёртывании.

Серверный режим OpenRouter поддерживает обычный Docker-listener `HOST=0.0.0.0`. Для его включения одновременно нужны `NODE_ENV=production`, `FUNBAN_TRENDWATCH_ENABLED=1`, `FUNBAN_OPENROUTER_SERVER=1`, режим `openrouter` и корректная конфигурация ключа/модели. По умолчанию ИИ выключен. Codex и старый runtime остаются ограничены loopback.

Все API ИИ остаются за действующей сессией Team Portal; недоступность портала закрывает доступ, чужой Origin отклоняется. Права совпадают с существующей авторизацией Funban: отдельное серверное ограничение «только лид» эта доработка не вводит. Публикуйте сервис только через существующий доверенный reverse proxy с HTTPS и Portal ForwardAuth. Локальный preview для production не используется.

## 1. Где хранить ключ

Ключ предоставляет владелец аккаунта и бюджета OpenRouter. Человеку, который только сливает PR, ключ не требуется. Получите его через корпоративный менеджер паролей; для сервера предпочтителен отдельный ключ `funban-server`.

В панели развёртывания откройте **серверный сервис Funban → переменные окружения / секреты** и добавьте `OPENROUTER_API_KEY` как секрет времени выполнения (runtime). Если используется Coolify, это переменные окружения ресурса Funban, доступные запущенному контейнеру, а не только этапу сборки. Конкретную панель и действующую схему развёртывания должен подтвердить администратор.

- Не добавляйте ключ в GitHub, PR, Dockerfile, build arguments, презентацию или переменные `VITE_*`.
- `.env.example` содержит только шаблон. `.env.openrouter.local` нужен для ноутбука и не переносится через Git.
- Если сервер использует env-файл, держите его вне репозитория с доступом только владельцу процесса (0600), подключайте через менеджер сервиса или `--env-file`. Сам `node server.mjs` env-файл автоматически не читает.
- Не передавайте ключ в аргументах команд и не выводите `env`, `docker inspect` или полный ответ провайдера в общий лог.

В OpenRouter задайте конечный лимит ключа **$5 без периодического сброса** для первого подключения. У аккаунта должен быть доступный баланс. Лимит не пополняет баланс и не означает цену одного анализа. Срок действия ключа согласуйте с владельцем и запишите дату ротации. Поле имени — метка, технической привязки к репозиторию оно не создаёт.

## 2. Настройки сервиса

| Переменная | Начальное значение | Назначение |
| --- | --- | --- |
| `OPENROUTER_API_KEY` | Секрет, отдельно от Git | Обычный API-ключ для генерации, не Management key |
| `OPENROUTER_PROXY_URL` | `http://weekly-news-ai-egress:8888` на prod01 | Приватный HTTP CONNECT-прокси только для OpenRouter |
| `FUNBAN_OPENROUTER_MODEL` | Точный ID выбранной модели | Обязательное значение вида `provider/model`; совместимость проверяется живым запросом |
| `FUNBAN_OPENROUTER_CLARIFY_MODEL` | Оставить пустым | Прежняя настройка, сейчас не используется: уточнения при вводе отключены |
| `FUNBAN_OPENROUTER_MAX_KEY_LIMIT_USD` | `5` | Максимальный разрешённый лимит ключа; не устанавливает лимит в OpenRouter |
| `FUNBAN_OPENROUTER_MAX_TOKENS` | `4096` | Максимум выходных токенов на анализ |
| `FUNBAN_OPENROUTER_TIMEOUT_MS` | `180000` | Общий тайм-аут запуска, 180 секунд |
| `FUNBAN_TRENDWATCH_MODE` | `openrouter` | Выбор адаптера |
| `FUNBAN_TRENDWATCH_ENABLED` | `0` при подготовке, `1` при согласованной проверке | Разрешение запусков ИИ |
| `FUNBAN_OPENROUTER_SERVER` | `1` | Явное разрешение OpenRouter на нелокальном listener в production |
| `HOST` | `0.0.0.0` | Доступность контейнера для reverse proxy; порт не публикуйте напрямую в интернет |
| `FUNBAN_TRENDWATCH_AUTO` | `0` | ИИ запускается только вручную; старое `1` сохраняет лишь бесплатное обслуживание просроченных карточек |
| `FUNBAN_TRENDWATCH_WEB` | `1` | Разрешить лёгкий поиск для рыночных идей и новых подходов |
| `FUNBAN_TRENDWATCH_CONCEPTS` | `1` | Профиль команды концепций |
| `NODE_ENV` | `production` | Обязательная серверная авторизация |

Модель должна поддерживать Responses API, строгий JSON Schema и инструменты. `openrouter/auto` и суффикс `:online` адаптер запрещает. Проверенного для production ID пока нет: его нужно выбрать, записать в настройках и проверить по шагу 5. Автоматической замены модели нет.

Сохраните существующие `FUNBAN_PUBLIC_URL`, настройки Team Portal и постоянное хранилище. В Docker по умолчанию `PORT=3000`, `FUNBAN_DATA=/data/state.json`; весь `/data` должен находиться на постоянном томе. Архив рекомендаций хранится рядом в `state.json.trendwatch/`. Не запускайте два backend с одним хранилищем. `FUNBAN_LOCAL_PORT=4338` относится только к локальному preview и для production не нужен.

Серверу нужен исходящий HTTPS к `https://openrouter.ai/api/v1` и доступ к действующему Team Portal. Веб-поиск выполняет OpenRouter; отдельный ключ Exa или Tavily этому адаптеру не нужен. Локальные Codex CLI, Python и MLX на сервер устанавливать не требуется.

На prod01 `docker-compose.yaml` подключает Funban к существующим сетям `coolify` и
`urgaqzc5und8ly1epxub8kzo`. Compose использует прежний внешний том данных и имя
сервиса Traefik, указанное в существующих маршрутах Funban. В Coolify используйте
Docker Compose из Git и Raw Compose, без автоматической генерации маршрутов
домена. Перед переходом проверьте текущие значения настроек ресурса и сделайте
свежий бэкап. Сохраните настройки Dockerfile для отката. При переключении
проверяйте, что одновременно запись в том выполняет только один контейнер Funban.
Публичные маршруты продолжают использовать существующую конфигурацию Traefik.

Прокси применяется только для запросов адаптера OpenRouter. Сбой прокси приводит
к ошибке запроса без прямого повтора. Запросы Portal и MCP идут своим прежним
маршрутом. Для изолированной проверки используйте отдельный том и отдельное имя
сервиса Traefik либо запускайте без публикации сервиса в Traefik.

ИИ-анализ запускается только явной кнопкой в карточке или командой переоценки бэклога. Ввод, добавление задачи, открытие карточки и наступление срока пересмотра не запускают модель. Уточнения при вводе также выключены: черновик не отправляется провайдеру. Это правило действует и при оставшемся `FUNBAN_TRENDWATCH_AUTO=1`.

## 3. Проверка конфигурации без сети

Выполните из `/app` внутри контейнера Funban, где уже доступны runtime-переменные:

```bash
node --input-type=module <<'JS'
import { openRouterConfig, openRouterConfigurationMessage } from './trendwatch-openrouter.mjs'
const message = openRouterConfigurationMessage()
if (message) { console.error(message); process.exit(1) }
const { model, maxTokens, timeoutMs, maxKeyLimit } = openRouterConfig()
console.log({ configuration: 'valid', model, maxTokens, timeoutMs, maxKeyLimitUSD: maxKeyLimit, networkRequests: 0 })
JS
```

Эта команда не печатает ключ и не делает запросов. `configuration: valid` означает только корректную форму настроек. Короткая альтернатива в контейнере и checkout — `npm run check:openrouter`; проверочный скрипт включён в образ. Ни одна из этих проверок не подтверждает активацию сервиса: её проверяет API на шаге 5.

## 4. Проверка ключа без генерации

Следующая команда выполняет один read-only запрос к OpenRouter, не запускает модель и не отправляет задачи. Запускайте её в том же окружении, не подставляя ключ в текст команды:

```bash
node --input-type=module <<'JS'
import { openRouterConfig } from './trendwatch-openrouter.mjs'
import { fetchOpenRouter } from './openrouter-fetch.mjs'
try {
  const { apiKey, maxKeyLimit } = openRouterConfig()
  const response = await fetchOpenRouter('https://openrouter.ai/api/v1/key', {
    headers: { Authorization: `Bearer ${apiKey}` },
    redirect: 'error', signal: AbortSignal.timeout(15000),
  })
  if (!response.ok) {
    await response.body?.cancel()
    console.error(`OpenRouter: HTTP ${response.status}`)
    process.exitCode = 1
  } else {
    const { data } = await response.json()
    const valid = Number.isFinite(data?.limit) && data.limit > 0 &&
      data.limit <= maxKeyLimit && Number.isFinite(data.limit_remaining) && data.limit_remaining > 0
    console.log({ keyAccepted: valid, limitUSD: data?.limit, remainingUSD: data?.limit_remaining })
    if (!valid) process.exitCode = 1
  }
} catch {
  console.error('Не удалось проверить конфигурацию или связь с OpenRouter; ключ и тело ответа скрыты.')
  process.exitCode = 1
}
JS
```

Успех: `keyAccepted: true`. Это проверяет доступ и требования к лимиту ключа, но не гарантирует совместимость модели или успех следующей генерации. [Документация проверки лимитов OpenRouter](https://openrouter.ai/docs/api_reference/limits).

## 5. Проверка приложения и первый платный анализ

Сначала используйте отдельное тестовое окружение с синтетической доской и отдельным томом. Не подменяйте рабочие данные демофайлами. До обновления production сохраните защищённую согласованную копию всего каталога данных при остановленных записях и идентификатор прежнего образа; проверьте возможность восстановления в изолированной среде.

После согласованного включения `FUNBAN_TRENDWATCH_ENABLED=1` и `FUNBAN_OPENROUTER_SERVER=1` в production, оставив `FUNBAN_TRENDWATCH_AUTO=0`:

1. Проверьте `/api/health`: ожидается HTTP 200. Это проверка приложения и чтения доски, **не OpenRouter**.
2. Проверьте авторизацию: без сессии `/api/state` возвращает 401; вход через Team Portal открывает доску. Не используйте mock portal на рабочем сервисе.
3. В авторизованной сессии проверьте `GET /api/items/<id>/trendwatch` для тестовой карточки: `mode: openrouter`, `available: true`, `automatic: false`. Если `available: false`, проверьте ключ/модель, `NODE_ENV`, `FUNBAN_TRENDWATCH_ENABLED` и `FUNBAN_OPENROUTER_SERVER`, не снимайте защиту.
4. Вручную запустите **один платный анализ** внутренней задачи: «Автоматизировать сбор материалов. Подтверждённая экономия — 2 часа в неделю с учётом проверки». Ожидаются расчёт пользы около 8 часов за четыре недели, объяснение балла и отсутствие поиска. Конкретный балл не фиксируется тестом.
5. Отдельно проверьте одну синтетическую задачу об исследовании нового рыночного подхода. В рекомендации должны быть применимые примеры и источники; в ответе API у готового задания — подтверждённый `webUsage.queries > 0`. Сверьте расход в кабинете OpenRouter. Внутренняя задача не должна иметь поисковых вызовов.
6. Проверьте сохранность: до подтверждения сохранённый балл не меняется; после изменения и подтверждения применяется балл человека, а предложение ИИ остаётся прежним. Во входящих подтверждение переносит задачу в бэклог, окно закрывается.
7. Перезапустите тестовый сервис и убедитесь, что доска и рекомендации сохранились. Зафиксируйте ID модели, commit/образ, дату, результаты двух сценариев и фактическую стоимость — без ключа и закрытого текста задач.

Проверьте ручной режим на изолированной доске: заполните и добавьте задачу, откройте рекомендацию — до нажатия «Получить ИИ-рекомендацию» нового запуска быть не должно. При перезагрузке страницы и наступлении срока пересмотра модель также не вызывается. Уже начатый вручную анализ продолжает работу после закрытия окна.

При ошибке не запускайте массовую переоценку. Server tools находятся в beta, поэтому доступность модели в каталоге сама по себе не подтверждает совместимость ответа с нашим валидатором. [Web Search Server Tool](https://openrouter.ai/docs/guides/features/server-tools/web-search).

## 6. Лимиты и ручной запуск

Текущая оценка концепций: проверка ключа, затем два последовательных запроса без автоматических повторов — выбор режима и сам анализ. Выбор режима получает только название, описание и комментарии текущей задачи, без поисковых инструментов и соседних карточек. Он выполняется при каждом ручном запуске как во входящих, так и в бэклоге.

На выбор режима выделяется до четверти общего лимита выходных токенов, максимум 1024. Из лимита анализа (по умолчанию 4096) вычитается фактический расход первого этапа; если провайдер его не сообщил — весь выделенный резерв. Тайм-аут 180 секунд общий для обоих этапов. В сохранённом usage суммируются токены двух ответов. Это дополнительный оплачиваемый запрос, а не бесплатная локальная классификация. Старые форматы оценки без адаптивного выбора режима сохраняют один запрос.

Для `bug` и `internal_improvement` второй запрос получает `tools: []`, фиксированный тип задачи, `searchOutcome: not_needed` и пустые источники. Для `market_idea` и `approach_research` поиск доступен только при `FUNBAN_TRENDWATCH_WEB=1`; при выключенном поиске инструменты отсутствуют у всех задач. Итоговая схема запрещает менять выбранный тип. Ошибка выбора режима останавливает запуск до анализа без повторов и изменений балла/положения карточки. Классификация остаётся решением модели и требует проверки на реальных примерах после выпуска. Поиск: Exa fast, до трёх вызовов, девяти результатов и трёх источников в рекомендации. Эти ограничения не задают фиксированную стоимость анализа. Лимит ключа контролируется у провайдера; отменённый или отклонённый валидатором ответ тоже может стоить денег.

Текст задачи, комментарии и контекст доски передаются через OpenRouter провайдеру модели. Запрошены `store:false` и `provider.data_collection=deny`; это не означает, что данные остаются на сервере. Перед production-проверкой владелец данных должен согласовать такую передачу. Для веб-поиска инструкции требуют только обезличенную публичную тему; это указание модели, а не отдельный гарантированный фильтр утечек.

Автоматические ИИ-запуски отключены в сервере, независимо от прежнего `FUNBAN_TRENDWATCH_AUTO`. Счётчики и красная подсветка вычисляются без модели. Значение `AUTO=1` сохраняет уже настроенное бесплатное обслуживание: перенос в «Не разобрано» спустя 14 дней после срока пересмотра, с сохранением балла и прежней стопки. При `AUTO=0` этот фоновый перенос остаётся выключенным — обновление не включает новые перемещения на рабочей доске. Переключать флаг ради ИИ не нужно.

Ручная команда «Переоценить бэклог» запускает очередь и может расходовать токены на каждую выбранную задачу; её можно остановить. При перезапуске сервера незавершённые задания помечаются прерванными, а не перезапускаются автоматически. Уже отправленный до остановки запрос мог быть оплачен.

## 7. Ошибки и остановка

`OPENROUTER_ROUTING` — первый этап не вернул допустимый режим; основной анализ не запускался. Сетевые ошибки и тайм-аут этого этапа имеют обычный код и этап «Выбор режима анализа». В диагностике последующего ответа показывается закреплённый режим; несовпадение `recommendation.assessmentKind` отклоняется проверкой схемы. Не запускайте массовые повторы при таком сбое.

| Симптом | Что проверить |
| --- | --- |
| ИИ недоступен, хотя health зелёный | `NODE_ENV=production`, `FUNBAN_OPENROUTER_SERVER=1`, `FUNBAN_TRENDWATCH_ENABLED=1`, режим, модель и наличие ключа |
| Ключ отклонён / HTTP 401 или 403 | Ключ активен, не истёк, правильно передан в runtime |
| Недостаточно средств / HTTP 402 | Баланс аккаунта и остаток бюджета ключа |
| Требуется конечный лимит | В OpenRouter лимит больше нуля, не более $5 и есть остаток; настройка приложения не меняет лимит провайдера |
| HTTP 429 | Ограничение частоты у провайдера; не создавать бесконечные повторы |
| Тайм-аут | Сеть или скорость выбранной модели; прежняя оценка сохранена |
| Ответ не прошёл проверку / ошибка формата | Откройте «Детали ошибки» и смотрите код и этап по инструкции ниже; валидатор не отключайте |

### Диагностика неудачного анализа

В карточке под сообщением об ошибке раскройте **«Детали ошибки»**. Передайте ответственному код, этап, длительность и ID запуска. Если доступны, там же будут HTTP-статус, сетевой код, причина незавершённого ответа или код отклонённой проверки. Ключ, описание задачи и полный ответ модели для диагностики пересылать не нужно.

- `OPENROUTER_NETWORK`: транспортный сбой при проверке бюджета (`budget`) или запросе модели (`generation`). Например, `ENOTFOUND` — DNS, `ECONNREFUSED` — отказ соединения. При настроенном прокси проверяйте и его; код сам по себе не доказывает, какой узел отказал.
- `OPENROUTER_TIMEOUT`: истёк общий лимит времени адаптера. Встроенные сетевые тайм-ауты могут приходить как `OPENROUTER_NETWORK` с кодом `UND_ERR_*_TIMEOUT`.
- `OPENROUTER_INCOMPLETE`: ответ модели не завершён. `max_output_tokens` означает достижение лимита выхода, `content_filter` — остановку фильтром. Не повышайте лимиты вслепую.
- `OPENROUTER_PROVIDER`: провайдер вернул ошибку выполнения. Исходный текст ошибки не сохраняется, поскольку может содержать закрытые данные.
- `OPENROUTER_JSON` / `OPENROUTER_SCHEMA`: ответ не читается как JSON либо нарушает формат оценки. Для схемы сохраняются число нарушений и до десяти кодов с известными путями полей, включая вложенные (например, `sources.0.relevance: invalid_value`), без их значений; неизвестные имена заменяются на `other`. Индексы источников начинаются с нуля. `invalid_value` — значение вне допустимого списка, `unrecognized_keys` — лишние поля; для `sources.*.relevance` разрешены только `direct` и `analogy`. Значения и названия лишних полей не сохраняются.
  При ошибке чтения JSON дополнительно сохраняются `parseIssue`, число элементов ответа, сообщений модели и текстовых частей, размер итогового текста в байтах и число токенов рассуждения (если провайдер передал его). `no_final_message` — нет завершающего сообщения ассистента; `empty_text` — пустой итог; `refusal` — отказ; `unfinished_message` — сообщение не завершено; `invalid_content` — неверная структура содержимого; `markdown` — текст обёрнут в Markdown; `non_json` / `invalid_json` — текст не читается как JSON. Эти признаки не содержат фрагментов ответа. Они не доказывают нехватку токенов: `completed` и общий расход сами по себе не повод увеличивать лимит.
  `answerFormat` показывает, откуда прочитан итог: `function_call` — аргументы `submit_priority`, `message` — текст JSON. При доступном поиске адаптер передаёт полную строгую схему через функцию `submit_priority`: она только возвращает данные, не выполняет действие и не подтверждает балл. Допускается ровно один завершающий вызов; неверный, повторный или незавершающий вызов отклоняется (`invalid_function_call`). Без поиска используется прежний `text.format`. Совместимый завершающий текстовый JSON также проходит те же проверки, если вызовов функций в ответе нет. Промежуточные сообщения не склеиваются с итогом; из них сохраняются только аннотации источников. Если итог повреждён или отсутствует, прежнее сообщение вместо него не используется. Проверки схемы, источников, лимитов и согласованности остаются обязательными; автоматического исправления JSON или платного повтора нет.
- `OPENROUTER_VALIDATION`: формат корректен, но содержимое отклонено. `PACKET_MISMATCH` — не совпал идентификатор задания или контекста; `UNKNOWN_WEB_SOURCE` — ссылка не подтверждена результатами поиска/цитатами провайдера либо повторяет уже указанный источник; `WEB_SEARCH_NOT_VERIFIED` — нет допустимого подтверждения поиска; `INCONSISTENT_PRIORITY_COMPARISON` — балл противоречит сравнению. Проверки остаются обязательными.
  Для `UNKNOWN_WEB_SOURCE` сохраняются только количества уникальных адресов (`searchResultUrlCount`, `citationUrlCount`, `verifiedUrlCount`) и до десяти проблем `sourceIssues`: номер источника **с единицы** и причина `not_in_search_results` или `duplicate_source`. Полные URL, поисковые запросы и фрагменты ответа в диагностику не попадают. Нулевое число адресов означает отсутствие доступных подтверждений, а не доказательство отсутствия самого поиска. Эти поля видны в «Деталях ошибки».
- `OPENROUTER_SEARCH_LIMIT` / `OPENROUTER_RESPONSE_SIZE`: счётчики поиска недопустимы либо превышен предел размера ответа.
- `OPENROUTER_INTERNAL`: ошибка подготовки или обработки на сервере, которую не удалось безопасно классифицировать.

Безопасные поля сохраняются в `errorCode` и `errorDiagnostics` файла `<FUNBAN_DATA>.trendwatch/<ID запуска>/job.json` и доступны через существующий авторизованный API как `job.failure`. Не пересылайте весь `job.json`: в нём есть контекст задачи. После перезапуска детали сохраняются. Для старых запусков, где причина уже потеряна, восстановить её нельзя: появится только прежний общий код.

Ошибки не меняют подтверждённый балл, не создают автоматических повторов и не переключают запрос на обходной маршрут. Повторный ручной запуск может быть платным; сначала изучите сохранённые детали.

Выбор строгой итоговой функции учитывает [описанный OpenRouter случай несоблюдения `text.format` вместе с инструментами](https://openrouter.ai/blog/tutorials/ai-code-review/). В их примере использована другая модель; это не доказательство причины конкретного сбоя `gpt-5-mini`. Локальные тесты проверяют контракт на синтетических ответах. После согласованного выпуска нужна одна проверка с реальным провайдером: итоговая функция, подтверждения источников и счётчики поиска должны совместно пройти валидацию. Для подтверждения URL используются аннотации `url_citation` и `action.sources` завершённых серверных элементов `openrouter:web_search` — [формат официального SDK](https://github.com/OpenRouterTeam/typescript-sdk/blob/main/src/models/outputwebsearchservertoolitem.ts). Учитываются только элементы `status: completed` без ошибки и адреса с `type: url` действия `search`. Если оба вида подтверждений отсутствуют, ссылки из аргументов функции не считаются доказательством поиска. URL из запросов, произвольного текста и других инструментов не принимаются. Сравнение сохраняет путь и query-параметры; разные страницы одного домена не считаются одним источником. Наличие URL в выдаче подтверждает его происхождение, но само по себе не доказывает достоверность каждого вывода модели. Лимиты токенов, поиска и расходов этой правкой не увеличиваются.

Для остановки новых запусков задайте `FUNBAN_TRENDWATCH_ENABLED=0` и `FUNBAN_TRENDWATCH_AUTO=0`, перезапустите сервис. Чтобы немедленно перекрыть расходы скомпрометированного ключа, владелец отзывает его в OpenRouter; отключение переменной не отменяет уже выполненную платную работу. Данные и архив исследований не удаляйте. Откат образа проверяйте с учётом совместимости данных; не восстанавливайте старую копию поверх новых пользовательских изменений без отдельного решения.

## Локальная проверка серверного режима

`npm run test:trendwatch` включает тесты конфигурации и HTTP-сценарий production-сервера: сессия, отказ портала, чужой Origin, анализ, сохранение отдельного балла человека, перезапуск и отключение запусков. Сетевой ответ OpenRouter синтетический; тестовый транспорт не включён в production-образ.

В CI тот же HTTP-сценарий выполняется внутри собранного Docker-образа на Node.js 22 с `HOST=0.0.0.0`, `--network none` и временными данными. Тестовые файлы монтируются только на время проверки. Ни реальный ключ, ни рабочая доска, ни внешний ИИ для этих проверок не используются.

`vercel.json` отключает автоматические Vercel-деплои только для ветки `codex/funban-ai-prioritization`. GitHub Actions для PR выполняет проверки и пропускает deploy. Это не запрещает деплой при будущем разрешённом слиянии в main: действующий workflow для main запускает Coolify, поэтому слияние и выпуск нужно согласовать отдельно.
